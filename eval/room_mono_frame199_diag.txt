## 2026-04-17 Simplification pass and failed threshold attack

Between V2 (`d4584b8`) and HEAD we ran an aggressive Tesla-style
cleanup pass (commits `c81bcf2`, `9fbf2de`, `0f9c114`, `d2676a3`,
`f2d7111`, `1af225d`, `776fd05`). Net: ~2325 tracked lines deleted
(experimental `score`/`pipeline` reference policies + harness + docs,
Phase B trace plumbing, four dead diagnostic prints, dead variables,
struct trimming) with **byte-identical trajectory SHAs for all five
gates**, i.e. zero behavioral change. Baseline drifted from
`room_mono = 0.176340` to `0.176506` only because `c81bcf2` removed
the V1 coarse-error tiebreak (plan.md already documented it as
near-noise).

After the cleanup, one targeted accuracy attempt was tried and
reverted:

- Hypothesis: lowering `kMinTrackLocalMapInliers` from `12` to `10`
  would let frames like 192 (9 post-PnP inliers) keep tracking instead
  of entering the lost -> relocalize -> cascade loop.
- Result: `xyz_mono` unchanged at `0.028136` (guardrail held; it never
  visits the 9-11 inlier regime), but `room_mono` regressed
  `0.176506 -> 0.290476` (+64.7%). Different SHA `2d4c8960de94298f`.
- Interpretation: the `12` minimum is a load-bearing safety valve.
  Accepting a marginal PnP solution with ~10 inliers produces a bad
  pose that then gets baked into `current_frame_->landmarks_` and
  pollutes downstream propagation. The old "reject -> relocalize" path
  was, on average, less harmful than "accept with 10 inliers".
- Add to ruled-out: any monotone reduction of `kMinTrackLocalMapInliers`
  without a companion pose-quality gate. If revisited, pair the lower
  threshold with tighter reprojection / pose-change checks rather than
  lowering the inlier count alone.

Two independent speculative attacks (V3 ultra-sparse skip, this
12->10 threshold) have now regressed `room_mono` by ~65-68% versus the
V2 baseline. The pattern is consistent: threshold or gating changes
that "let more frames through" tend to accept bad state, which
cascades, which is worse than the localize/recover path. The next
concrete room_mono lever is therefore *not* another threshold knob
but something structural like reference-KF refresh under a dying
propagation chain - and even that is a new-handoff-sized experiment
given the failure rate of speculative attempts.

## 2026-04-18 600-frame async crash is a threading race

Running `./build_codex/run_mono --tum data/tum/rgbd_dataset_freiburg1_room
--max-frames 600 --no-viz data/ORBvoc.txt` three times with loop closing
and mapping threads live (default async mode) produced one clean core
dump at ~frame 195 during a relocalize cascade. Under `--repro-eval`
(synchronous mapping, loop closing disabled) the same sequence ran
three times with exit=0 and produced an identical ATE of 0.468671 m
on every rep. An AddressSanitizer build ran a clean async 600-frame
pass with zero memory errors and no crash, but ASan slows the tracker
enough that the timing-sensitive path does not fire.

Conclusions:

- The crash is a threading race, almost certainly in the handoff
  between Tracking, LocalMapping, and LoopClosing rather than a
  single-threaded bug. `--repro-eval` dodges it entirely by removing
  the LoopClosing thread.
- A proper fix needs ThreadSanitizer (not AddressSanitizer) plus many
  run reps to find the race, and then careful mutex / atomic audit on
  Map::getAllKeyframes() / getAllLandmarks() and the LoopClosing
  pose-graph handoff. Plan.md §6.1 already flags this as a known
  concern in "Map API hygiene".
- Async 600-frame ATE variance (0.48–0.93 m across three reps) is
  large enough that single-rep comparisons are not meaningful for
  that window; head-250 gates stay the reliable signal.

Practical recommendation recorded for the next session: anyone
running 600-frame loop-enabled mono for measurement should prefer
`--repro-eval` unless they are explicitly testing the loop thread.

## 2026-04-18 ThreadSanitizer race triage

Built with `-fsanitize=thread -fno-omit-frame-pointer -g` and ran
`setarch $(uname -m) -R env TSAN_OPTIONS=... ./build_tsan/run_mono
--tum data/tum/rgbd_dataset_freiburg1_room --max-frames 250 --no-viz
data/ORBvoc.txt` (ASLR off via `setarch -R` to avoid TSan's
"unexpected memory mapping" FATAL under newer kernel mmap randomness).

First pass before any fix: 27 data races + 2 lock-order-inversions.
Top hit by location: `src/core/landmark.h:30/31` -- plain `bool is_bad_`
raced between `Optimizer::bundleAdjustment -> Landmark::setBad()`
on the LocalMapping thread and `Tracking::needNewKeyframe ->
Landmark::isBad()` on the main thread.

Fix landed in commit ff74140: `is_bad_` is now `std::atomic<bool>`
with release-store / acquire-load accessors, no behavior change on
any of the seven regression gates.

Post-fix TSan rerun: 34 data races (variance across runs; slightly
higher but no longer featuring `landmark.h:30`). The remaining races
fall into two buckets:

1. `std::shared_ptr<Landmark>` access on shared containers --
   `shared_ptr_base.h:1670 operator bool() const` and
   `shared_ptr_base.h:1075 __shared_count(...)` copy construct --
   flagged when main-thread `needNewKeyframe` / `trackLocalMap`
   iterate `Keyframe::landmarks_` while LocalMapping swaps entries.
   Fixing this requires a container-level lock (e.g. hold
   `Keyframe::mutex_` around the landmark iteration, or introduce a
   snapshot getter) rather than a one-line atomic change.
2. `Tracking::current_frame_` shared_ptr swap: main thread
   `addFrame()` assigns at tracking.cc:283 while the LocalMapping
   thread's `onBACompleted` callback dereferences `current_frame_`
   via `recomputeCurrentPose` (tracking.cc:1911). `pose_mutex_`
   already exists; a minimal fix is to hold it across the swap and
   around the callback read.

Both are real races and plausibly related to the 600-frame async
intermittent core dump described in the previous section. Each
needs a targeted fix with the same scope-and-gate discipline as the
is_bad_ atomic; deferring to a follow-up session so the fix can
ship with its own TSan-verified "before / after" evidence.

## 2026-04-18 race fix progress

Three targeted race fixes landed on this branch. TSan race counts on
`./build_tsan/run_mono --tum data/tum/rgbd_dataset_freiburg1_room
--max-frames 250 --no-viz data/ORBvoc.txt` under `setarch -R`:

  before any fix                                      27 races
  after ff74140 (Landmark::is_bad_ -> atomic<bool>)   34 races (variance, target race 0 hits)
  after a2f65f1 (pose_mutex_ pairs current_frame_)    37 races (variance, target race 0 hits)
  after 996aefb (Keyframe::landmarks_ under kf mutex) 23 races

TSan run-to-run variance is ~10% on this workload, so the hard signal
is that each targeted race's symptom in its specific hot spot drops
to zero after its fix. Net useful deltas on this branch:

  * `Landmark::is_bad_`: gone.
  * `Tracking::current_frame_` shared_ptr swap: gone.
  * `Keyframe::landmarks_` primary iteration (trackLocalMap
    add_landmarks_from_kf): gone.

What is left in the 23 still-reported races:

1. `Tracking::recomputeCurrentPose` iterates `current_frame_->landmarks_`
   on the LocalMapping thread (via `onBACompleted`) while the main
   thread writes to the same vector in `trackReferenceKeyframe`,
   `trackLocalMap`, relocalization, and KF promotion paths. `Frame`
   already declares `std::mutex mutex_` but nothing currently takes
   it; fixing this cleanly needs *both* the callback-side snapshot
   *and* locks on every main-thread write site -- many sites across
   tracking.cc.
2. `LocalMapping::mapPointCulling` removes landmarks via
   `removeLandmark(lm)` concurrently with reads from Tracking; the
   Map side appears to need a container-level lock on top of the
   per-entity locks that already exist.

Neither is a one-commit fix. They stay as follow-ups for a dedicated
session with the same discipline applied here (one race per commit,
TSan before/after, all seven gates byte-identical).
